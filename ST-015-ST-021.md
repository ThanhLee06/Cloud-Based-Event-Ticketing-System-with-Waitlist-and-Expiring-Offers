

## 1. Phạm vi triển khai

Phần này được triển khai trên cấu trúc hiện có của dự án: NestJS + Prisma + PostgreSQL ở Backend và Next.js + React + TypeScript ở Frontend.

- ST-015: tái sử dụng `Reservation`, `IdempotencyRecord` đã có trong `backend/prisma/schema.prisma`; bổ sung fingerprint request cho idempotency.
- ST-016: thêm `POST /api/reservations`, khóa dòng sự kiện bằng `SELECT ... FOR UPDATE`, kiểm tra sức chứa và tạo lượt giữ vé trong transaction.
- ST-017: bắt buộc header `Idempotency-Key`; cùng key và cùng yêu cầu trả lại response cũ; dùng key khác payload hoặc endpoint sẽ nhận HTTP 409.
- ST-018: thêm `GET /api/reservations/:id`, chỉ chủ sở hữu mới được xem; kết nối trang Checkout lấy reservation thật.
- ST-019: thêm `POST /api/reservations/:id/confirm`, tạo mã vé và biên lai JSON trong cùng transaction, chuyển `reserved_count` sang `sold_count`.
- ST-020: thêm `GET /api/reservations/me` và `DELETE /api/reservations/:id`; thao tác hủy chỉ giảm bộ đếm đúng một lần và kích hoạt FIFO promotion.
- ST-021: thêm API client Frontend; trang đặt vé, Checkout và Vé của tôi gọi API thật khi sự kiện/đơn đặt vé thuộc Backend.

## 2. Các endpoint

Tất cả endpoint bên dưới yêu cầu JWT Bearer Token.

| Method | Endpoint | Mục đích |
|---|---|---|
| POST | `/api/reservations` | Tạo lượt giữ vé (mỗi lượt 1 vé) |
| GET | `/api/reservations/me` | Danh sách vé/giữ chỗ của tài khoản hiện tại |
| GET | `/api/reservations/:id` | Chi tiết lượt giữ chỗ; có Ownership Guard |
| POST | `/api/reservations/:id/confirm` | Xác nhận thanh toán mô phỏng, sinh vé và biên lai |
| DELETE | `/api/reservations/:id` | Hủy giữ chỗ/vé, giải phóng sức chứa |

Các request ghi dữ liệu cần gửi `Idempotency-Key` (tối đa 80 ký tự, chỉ gồm chữ, số, dấu `. _ : -`).

### Ví dụ tạo lượt giữ vé

```http
POST /api/reservations
Authorization: Bearer <access_token>
Idempotency-Key: hold-event-001-try-1
Content-Type: application/json

{
  "eventId": "<event-uuid>",
  "quantity": 1
}
```

Thời gian giữ vé là 10 phút theo giờ PostgreSQL. Backend khóa dòng `events` trước khi kiểm tra `sold_count + reserved_count < capacity`, sau đó tạo Reservation và tăng `reserved_count` trong cùng transaction.

### Xác nhận thanh toán

```http
POST /api/reservations/<reservation-uuid>/confirm
Authorization: Bearer <access_token>
Idempotency-Key: confirm-<reservation-uuid>
```

Đây là luồng xác nhận thanh toán mô phỏng của bài tập; chưa tích hợp cổng thanh toán bên ngoài. Khi thành công, Reservation chuyển `HOLD` → `CONFIRMED`, có `ticketCode`, `confirmedAt`, `receiptContent`; Event giảm `reserved_count` và tăng `sold_count`.

### Hủy vé

```http
DELETE /api/reservations/<reservation-uuid>
Authorization: Bearer <access_token>
Idempotency-Key: cancel-<reservation-uuid>
```

Nếu trạng thái trước đó là `HOLD`, giảm `reserved_count`; nếu là `CONFIRMED`, giảm `sold_count`. Sau khi trả chỗ, Backend gọi `WaitlistService.promoteNextWaitlist()` trong cùng transaction để xét người đầu hàng FIFO. Reservation từ `WAITLIST_OFFER` tiếp tục được xử lý qua API Offer hiện có, tránh làm sai trạng thái Waitlist/Offer.

## 3. Thiết kế và bất biến dữ liệu

1. `reservations_active_user_event_key` là partial unique index đã có: mỗi user tối đa một reservation `HOLD` hoặc `CONFIRMED` cho cùng event.
2. Event row lock tuần tự hóa các thao tác giữ, xác nhận, hủy và cấp Offer trên cùng sự kiện.
3. `IdempotencyRecord.requestId` được tạo theo dạng `<userId>:<key>`; PostgreSQL advisory transaction lock tránh hai request cùng key cùng xử lý song song.
4. `request_hash` lưu SHA-256 fingerprint; dùng lại key cho endpoint hoặc payload khác sẽ bị từ chối HTTP 409.
5. Quyền sở hữu được kiểm tra tại Backend, không dựa vào userId do Frontend gửi.
6. Các thay đổi Reservation và bộ đếm Event nằm trong cùng transaction.

## 5. Cách chạy và cập nhật database

Tại thư mục gốc:

```bash
docker compose up -d
```

Backend:

```bash
cd backend
pnpm install
# Tạo backend/.env từ backend/.env.example và cấu hình DATABASE_URL
pnpm prisma:generate
pnpm prisma:deploy
pnpm typecheck
pnpm start:dev
```

Frontend:

```bash
cd frontend
pnpm install
# NEXT_PUBLIC_API_URL mặc định là http://localhost:4000/api
pnpm typecheck
pnpm dev
```

Nếu môi trường local chưa chạy các migration trước đó, dùng `pnpm prisma:migrate` thay cho `pnpm prisma:deploy` trong lần phát triển đầu tiên.

## 6. Checklist kiểm thử thủ công

- [ ] Đặt vé khi sự kiện còn chỗ → tạo một Reservation `HOLD`, `reserved_count` tăng 1.
- [ ] Gửi lại cùng `Idempotency-Key` và cùng body → nhận lại response cũ, không tăng `reserved_count` lần hai.
- [ ] Dùng lại key với body khác → HTTP 409.
- [ ] Hai tài khoản cùng đặt chỗ cuối cùng → chỉ một request thành công; request còn lại nhận hết vé.
- [ ] User A gọi chi tiết Reservation của User B → HTTP 403.
- [ ] Xác nhận thanh toán → có `ticketCode`, `confirmedAt`, `receiptContent`; `reserved_count` giảm 1 và `sold_count` tăng 1.
- [ ] Gửi lại xác nhận với cùng key → response cũ; không tăng `sold_count` lần hai.
- [ ] Hủy Reservation `HOLD` → `reserved_count` giảm 1.
- [ ] Hủy Reservation `CONFIRMED` → `sold_count` giảm 1.
- [ ] Hủy lại vé đã hủy → không giảm bộ đếm thêm lần nữa.
- [ ] Khi hủy/giải phóng chỗ và có người chờ → FIFO promotion được gọi trong transaction.
- [ ] Reservation thuộc Offer → phải đi qua API Offer, không hủy trực tiếp bằng Reservations API.
